# Tuntu v0.1 开发计划

## 1. 计划状态

| 项目 | 内容 |
|---|---|
| 对应需求 | `docs/PRD-v0.1.md` |
| 当前阶段 | M0–M9 全部完成；本地 `0.1.0` 已通过发布前验收 |
| 开发方式 | 本地优先、测试驱动、逐里程碑验收 |
| 版本目标 | `0.1.0` |
| 代码发布 | 未经用户明确要求，不 commit、不 push、不创建 PR、不发布镜像 |

## 2. 执行原则

1. **先证伪高风险假设**：先验证 CloudDrive2 的提交和完成能力，以及真实数据源是否可用。
2. **TDD**：每个行为先写失败测试或可复现探针，再做最小实现，最后运行回归。
3. **只做 v0.1**：不顺手加入 qBittorrent、PT、`.torrent`、通用来源编辑器或通知。
4. **保持简单**：单应用、单进程、SQLite、Jinja，不引入 Redis、Celery、React 或 Node 构建链。
5. **领域先行**：规范化、规则、排序、去重和状态机不依赖 FastAPI、数据库或真实来源。
6. **真实下载晚接入**：自动提交开关在 dry-run、幂等和秘密脱敏测试通过前保持不可用。
7. **测试内容合规**：仓库 Fixture 使用虚构数据；CD2 实机测试只使用合法公开资源和独立测试目录。
8. **历史诚实**：不把提交成功写成下载完成，不覆盖历史配置快照和筛选证据。

## 3. 技术基线

### 3.1 运行时

- Python 3.12。
- FastAPI + Uvicorn：Web 与 `/api/v1`。
- Jinja2 + 原生 JavaScript/CSS：管理后台。
- SQLAlchemy 2 + Alembic：SQLite 与迁移。
- Pydantic Settings：启动配置、环境变量和秘密覆盖。
- httpx：Provider HTTP 请求；按需启用 SOCKS 支持。
- grpcio：CloudDrive2 官方 gRPC 客户端；生成代码固定到经验证的 proto 版本。
- APScheduler：单进程每日计划和轮询触发，不向用户暴露 Cron。
- Argon2id：管理员密码哈希。
- 标准库 logging：结构化字段、脱敏过滤和轮转。

除非实现或测试证明必须，否则不再增加基础设施依赖。

### 3.2 测试

- pytest：单元、数据库、API 和服务测试。
- `httpx.MockTransport` 或等价轻量方式：HTTP Fixture 测试。
- FastAPI TestClient/ASGI transport：API 集成测试。
- Playwright Python：只覆盖发布必需的浏览器路径，放在后期引入。
- `live` 测试：真实 Provider 和 CD2，仅手工执行，不进入默认 CI。

### 3.3 进程与数据

- 官方只支持一个应用实例、一个 Uvicorn worker。
- API、调度器、轮询器运行于同一进程。
- `/data/tuntu.db` 为默认数据库。
- `/data/backups` 保存最近 3 份迁移前备份。
- `/data/logs` 保存最多 30 天轮转日志。
- 不使用 Redis、Celery、外部数据库或独立前端服务。

### 3.4 目标目录结构

目录按实现需要逐步创建，不预建空目录：

```text
Tuntu/
├── src/tuntu/
│   ├── models.py             # 内容中立领域模型与状态枚举
│   ├── contracts.py          # Provider、DownloadClient 等接口
│   ├── magnet.py             # v1 BTIH 解析与规范化
│   ├── normalization.py      # 内容标识、证据与候选合并
│   ├── rules.py              # 三态、体积、做种数、关键词规则
│   ├── selector.py           # 稳定排序与 Top 1
│   ├── pipeline.py           # 发现、聚合、评估、选择
│   ├── db/                   # ORM、Repository、迁移和备份
│   ├── providers/            # v0.1 内置来源
│   ├── downloaders/          # CloudDrive2
│   ├── services/             # Run、提交、轮询、审计
│   ├── scheduler.py          # 每日计划、互斥和轮询触发
│   ├── api/                  # FastAPI 路由与响应模型
│   ├── templates/            # Jinja 页面
│   ├── static/               # 原生 CSS/JS
│   └── cli.py                # Setup Token 与密码重置
├── migrations/
├── tests/
│   ├── unit/
│   ├── fixtures/
│   ├── integration/
│   ├── e2e/
│   └── live/
├── docs/
└── docker/
```

M2 已将 pre-alpha 草图精准改造成 `models.py`、`magnet.py`、`normalization.py`、`rules.py`、`selector.py` 和纯内存 `pipeline.py`，并删除复杂 Route。后续里程碑只在需要时增加数据库、Provider、下载器和 Web 文件，不为目录整齐预建空实现。

## M1：外部依赖风险验证

这是第一个开发里程碑。只写最小探针和测试资产，不开始 Web UI。

### M1.1 CloudDrive2 探针

#### 先写验证清单

- 错误凭据会明确失败且不泄露秘密。
- 正确凭据能完成健康检查。
- 合法测试 magnet 能提交到专用测试子目录。
- 明确拒绝、网络超时和结果不明能被区分。
- 重复提交时能观察 CD2 的实际行为。
- 能否取得外部任务 ID。
- 能否查询 `submitted`、`downloading`、`completed`、`failed`。
- 若任务 API不足，能否通过目标目录文件存在且大小稳定确认完成。

#### 实施

1. 记录当前 CD2 版本、可用协议/API 和认证方式。
2. 使用只读请求完成版本、认证和目录能力探测。
3. 经明确测试配置提交一个合法公开小型 magnet 到独立目录。
4. 保存脱敏请求/响应 Fixture；删除密码、Cookie、Token 和内网特有信息。
5. 输出一份能力矩阵，选择完成适配方案：
   - A：任务 API 直接确认。
   - B：提交响应 + 目标目录基线差异和文件稳定检测；任务状态可作为补充信号。
   - C：无法可靠确认。

#### 硬门槛

- A 或 B 才允许继续以正式 v0.1 为目标。
- 若只有 C，可继续开发预览版，但发布计划必须保持阻塞，不能降低 `completed` 语义。

### M1.2 真实来源探针

#### 探测范围

- JavDB 网页日榜、周榜、月榜，以及按番号搜索详情后提取的磁力候选。
- JavDatabase 周榜 Feed。
- Sukebei RSS。
- Knaben API。
- Bitsearch API。

#### 实施

1. 为每个来源写一个手工 `live` 探针，设置超时、User-Agent 和低访问频率。
2. 记录 HTTP 状态、响应类型、字段/DOM 稳定性、是否需要登录或挑战、一次请求成本。
3. 默认只把无需登录、Cookie、验证码和浏览器自动化的来源列为 v0.1 可用；JavDB 允许管理员显式配置自己的有效会员 Cookie 和 User-Agent，不自动提取浏览器会话。
4. 从有效响应提取最小脱敏 Fixture；测试数据替换为虚构标识和测试 BTIH。
5. 为失效来源记录失败类型，不通过绕过访问控制“修复”。

#### 完成标准

- 至少一个榜单源具备可实现路径。
- 至少两个候选源具备可实现路径。
- 每个内置来源都有“可用、暂不可用或降级”的明确结论和证据日期。
- 如果最低来源数量不足，先寻找符合相同公共访问原则的替代源，再进入 M4。

## M2：核心领域、magnet、规则与选择

状态：已完成（2026-08-13），19 项离线测试全部通过。

### M2.1 领域模型测试

先写失败测试覆盖：

- `ContentItem(namespace, raw_key, normalized_key)` 的身份和跨来源排名合并。
- 同一内容保留全部来源和排名，展示最优排名。
- 40 位十六进制与 32 位 Base32 BTIH 规范成同一值。
- Tracker、显示名和参数顺序不同的 magnet 合并为同一 Candidate。
- 缺失 `btih`、非法 BTIH、纯 `btmh` 被拒绝。
- `yes/no/unknown` 三态属性和证据不丢失。
- 未知体积与做种数不再使用 `0` 表示。

### M2.2 规则测试

先写参数化测试覆盖：

- 中文字幕、无码、UHD 的“不限/仅/排除”三态真值表。
- 体积上下限，以及启用规则时的未知体积拒绝。
- 最少做种数，以及未知做种数拒绝。
- 包含关键词任一匹配、排除关键词任一命中、忽略大小写。
- 一个候选同时产生多个拒绝原因。
- 新 RuleSet 无偏好，只执行有效性清洗。

### M2.3 排序与选择测试

- 已知做种数在未知之前，做种数降序。
- 已知体积在未知之前，体积升序。
- 相同值按 BTIH/来源稳定排序。
- 每个内容只选择第一个合格候选。
- `no_candidate` 与 `filtered` 是正常内容结果，不是异常。

### M2.4 最小实现

1. 精准调整现有领域模型，不保留为未来功能服务的 torrent/qB 行为。
2. 新增 v1 magnet 解析和规范化。
3. 将来源证据与聚合结果分离。
4. 实现规则集、Evaluation、稳定 Selector 和纯内存 Pipeline。
5. 保留清晰的 Provider 与 DownloadClient 接口，但不做动态插件加载。

### 完成标准

- 领域测试不依赖网络、FastAPI 或 SQLite 文件。
- 同一输入重复运行得到相同合并、规则和选择结果。
- 不存在“未知值被当作否/0”的代码路径。
- 自动管线输出最多每个内容一个选中候选。

## M4：内置 Provider 与来源健康

状态：已完成（2026-08-13），54 项测试全部通过；两个榜单路径和三个候选路径完成脱敏 live 复核，Bitsearch 作为弱覆盖可选源。

### M4.1 Provider 基础设施

先写测试：

- 单个来源超时不取消其他来源。
- 正常空结果记成功，HTTP/解析错误记失败。
- 同一 Run 相同查询只请求一次。
- 有效缓存可跨相邻 Run 复用，过期后重新请求。
- 重试次数有限并执行退避；连续失败不自动禁用。
- 代理只作用于公网 Provider，CD2/局域网默认绕过。
- 健康记录包含延迟、结果数、最近错误和连续失败次数。

### M4.2 Provider 实现顺序

按 M1 可用性结论，不盲目实现失效源：

1. 最稳定的榜单 Provider。
2. 第二个同周期榜单 Provider，验证跨榜单合并。
3. 最稳定的两个候选 Provider。
4. 其余通过 M1 的内置 Provider。
5. JavDB 详情候选作为发现/候选组合来源。

每个 Provider 必须：

- 返回原始标识、规范化标识和来源证据。
- 使用最小离线 Fixture 测试正常、空结果和结构变化失败。
- 不保存完整原始响应；仅解析热榜展示所需的封面 URL 和原始条目 URL。
- 公共页面无需登录；受限页面仅使用管理员显式配置的有效会员 Cookie，不自动登录、不读取浏览器 Cookie，也不处理验证码或访问挑战。

### M4.3 手工番号

- 选择 Profile 后继承候选源、规则、排序和目标目录。
- 使用 Provider 的编号规范化，不做跨命名空间模糊猜测。
- 保存为手工触发 Run，与自动 Run 使用同一管线。

### 完成标准

- 至少一个榜单源、两个候选源通过 Fixture 和手工 live 探测。
- AC-02、AC-03、AC-05、AC-08 的来源部分通过。
- 任一 Provider 失败不会丢失其他 Provider 的结果。

## M5：CloudDrive2、下载状态机与全局幂等

状态：已完成（2026-08-13），86 项离线测试全部通过，其中 38 项聚焦 CD2 配置、gRPC 适配、状态机、完成判定、幂等与迁移；M1 合法公开资源实机闭环作为外部验证依据。

### M5.1 DownloadClient 契约

定义最小能力：

- `health_check()`。
- `submit(magnet, destination, idempotency_context)`。
- `get_status(external_reference)`。
- `verify_completion(external_reference, destination)`。

统一错误分类：认证失败、配置错误、明确拒绝、网络错误、结果不明、外部任务失败。

### M5.2 状态机测试

先写测试覆盖：

- `submitting → submitted → downloading → completed`。
- 明确拒绝进入 `failed`。
- 网络超时保持结果不明，只允许原候选重试。
- 超过可配置的“需要关注”阈值进入 `attention_required`，默认阈值为 24 小时。
- 轮询错误不覆盖最后可靠状态。
- 人工完成必须二次确认并产生人工审计事件。
- 非法状态跳转被拒绝。

### M5.3 全局幂等与回退测试

- 两个 Profile 同内容、不同目录时只允许一次自动提交。
- 两个 Profile 同 BTIH 时只允许一次自动提交。
- 明确同步拒绝第一候选后可尝试下一候选。
- 结果不明时不得换候选。
- CD2 接受后失败不得换候选。
- `failed` 普通重试保留历史。
- `submitted/completed` 或绕过去重的重提必须二次确认并关联旧任务。

### M5.4 CD2 实现

1. 按 M1 能力矩阵实现认证、健康检查和 magnet 提交。
2. 建立 CD2 配置对象：endpoint、认证模式/API Token/账号密码、TLS 校验与 CA、全局根目录、测试子目录、轮询间隔和关注阈值；领域层不得引用具体 NAS 地址或路径。
3. 在数据库事务中先创建提交占位，再调用外部客户端。
4. 规范化“全局根目录 + Profile 固定子目录”，拒绝空路径和越界路径。
5. 保存脱敏外部引用和原始错误分类。
6. 按 A/B 方案实现可靠完成检测。
7. 不实现取消、删除或远程清理。

### M5.5 直接 magnet

- 解析、规范化和去重预览。
- 可选标题，不参与 BTIH 身份。
- 普通提交一次确认，强制重复二次确认。
- 使用所选 Profile 的固定目标目录。

### 完成标准

- 使用 Mock CD2 覆盖所有错误分支和状态跳转。
- 使用合法测试资源完成一次实机提交与完成确认。
- AC-05、AC-06、AC-07、AC-09、AC-10 通过。
- 未通过并发幂等测试前，不开放自动提交。

## M6：Run 编排、每日调度、缓存与恢复

状态：已完成（2026-08-13），109 项离线测试全部通过；Run 编排、来源降级、预演/自动提交、候选回退、并发互斥、每日计划、缓存并发和下载恢复均已覆盖。

### M6.1 Run Service 测试

## M7：认证、设置、REST API 与安全

- 连接测试验证 Token 必要权限并报告缺失项，但不自动创建 Token 或扩大权限。
- GET 设置只返回掩码/是否配置。
- 密码、Token、Cookie、Authorization 在 API、异常和日志中均被脱敏。
- 公网代理和局域网 bypass 行为正确。
- `/data` 秘密文件/数据库权限符合容器用户最小权限。

### M7.3 `/api/v1` 资源

- `/api/v1/auth`：初始化、登录、退出、修改密码。
- `/api/v1/profiles`：列表、创建、编辑、归档、恢复、立即运行。
- `/api/v1/manual`：手工番号、magnet 预览与确认。
- `/api/v1/runs`：列表、详情、来源结果、内容与 Evaluation。

- `/api/v1/settings`：系统、代理和 CD2。
- `/api/v1/exports/downloads.csv`：历史导出。

## 8. 风险与处理规则

| 风险 | 影响 | 处理规则 |
|---|---|---|
| CD2 无可靠完成 API | 不能满足核心闭环 | M1 尝试文件稳定检测；仍失败则只做预览版，阻塞正式 v0.1 |
| 公开来源失效或反爬 | 榜单/候选不足 | 多来源、Fixture、健康状态；不绕过登录和挑战，寻找公开替代源 |
| 标题属性误判 | 规则误筛选 | 三态 + 证据；不确定标记 unknown，不猜成 yes/no |
| 网络超时后重复提交 | 重复下载 | 事务占位、全局 BTIH/内容锁、原候选反查，不自动换候选 |
| SQLite 并发锁 | Run 或轮询异常 | 单进程、小并发、短事务、显式重试和数据库幂等 |
| 代理误伤局域网 CD2 | 下载器不可达或泄露内网请求 | Provider 默认代理、CD2 默认 bypass，并写测试 |
| 秘密进入日志/Fixture | 安全事故 | 统一脱敏过滤、响应模型、Fixture 清洗和发布前扫描 |
| v0.1 范围再次膨胀 | 闭环迟迟不能完成 | 排除项只能进入后续版本文档，不在实现中预埋复杂 UI/基础设施 |

## 10. 每个任务的完成定义

一个开发任务只有同时满足以下条件才算完成：

1. 有对应的失败测试、Fixture 或可复现探针。
2. 使用满足需求的最少代码实现。
3. 新测试和相关回归测试全部通过。
4. 错误分支、日志和秘密处理已验证。
5. 没有顺带扩大 v0.1 范围。
6. 必要文档与实际行为同步。
7. 未经用户明确要求，不进行 Git commit、push、PR 或发布。
