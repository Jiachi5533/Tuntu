# Tuntu v0.1 产品需求文档

## 1. 文档信息

| 项目 | 内容 |
|---|---|
| 产品名称 | Tuntu（吞吐） |
| 版本 | v0.1 |
| 状态 | `0.1.0` 本地实现、真实 CD2 闭环和 Docker 双架构验收完成 |
| 产品形态 | 开源、自托管 Web 服务与 Docker 镜像 |
| 核心定位 | 内容中立的 BitTorrent 自动化控制面 |
| v0.1 首要闭环 | JAV 榜单/手工番号 → 公开磁力聚合 → 清洗筛选 → CloudDrive2 → 115 |
| 目标环境 | 单用户家庭 NAS、可信局域网、单实例单进程 |

## 2. 产品愿景

Tuntu 从不同来源“吞入”用户想要的内容和公开 BitTorrent 候选，经规范化、去重、过滤和排序后，将合格磁力“吐出”给下载客户端。

Tuntu 不实现 BitTorrent 协议，也不是另一个 qBittorrent。它负责的是下载前后的自动化控制和可追溯记录：

```text
内容发现 → 候选聚合 → 前置清洗 → 规则评估 → 候选选择 → 下载提交 → 状态跟踪
```

项目最初解决 JAV 热榜自动下载，但核心模型不得写死“番号”或成人内容。未来可以通过新的 Provider 和 DownloadClient 支持热门电影、剧集、通用 RSS、PT 或其他合法来源，而不重写核心管线。

## 3. 要解决的问题

- 榜单站、详情页、RSS 和公开 BT 索引的数据结构不一致。
- 同一个内容和同一个 BTIH 可能被多个来源反复返回，容易重复下载。
- 标题里的中文字幕、无码、UHD、体积和做种数常有缺失或冲突，不能简单当作确定事实。
- 用户需要知道一个候选为什么被接受、过滤、跳过或提交失败。
- 外部下载器“接受任务”不等于文件已经下载完成，状态不能混为一谈。
- 公开站点会失效、超时或改变页面结构，单个来源故障不能拖垮整次运行。
- 黑盒项目无法维护；Tuntu 必须是可审计、可测试、可扩展的开放源码项目。

## 4. 产品原则

1. **默认安全**：新订阅默认预演，不自动提交下载。
2. **状态诚实**：严格区分已提交、下载中和已完成；没有证据就不标记完成。
3. **全程可解释**：保存来源证据、配置快照、规则结果和状态事件。
4. **先清洗再下载**：只把选中的合格磁力交给 CloudDrive2，不把全部垃圾候选下放给下载器筛选。
5. **全局幂等**：同一 CloudDrive2 实例内默认不重复提交相同内容或 BTIH。
6. **局部故障隔离**：一个来源或一条坏数据失败时，其余来源继续。
7. **内容中立**：核心只理解 ContentItem、Candidate 和 DownloadTask；JAV 语义留在 Provider。
8. **首版克制**：v0.1 只完成 CD2 闭环，不复刻 Byte Muse 的全部功能。

## 5. v0.1 范围

### 5.1 必须交付

- 一个真实 JAV 榜单源能产生规范化内容条目。
- 至少两个候选源能查询、合并并去重公开 magnet。
- 支持手工番号查询和直接 magnet 提交。
- 支持中文字幕、无码状态、UHD、体积、做种数和关键词规则。
- 每个内容自动选择一个最优合格候选。
- 通过一个 CloudDrive2 实例下载到 115 挂载目录。
- 可靠跟踪下载完成；也允许用户明确进行“人工确认完成”。
- SQLite 持久化订阅、运行、来源证据、筛选结果和下载历史。
- 提供人物、系列和关键词关注清单，分离作品元数据管理与下载授权。
- 提供每日定时运行、手工运行、默认预演和来源故障隔离。
- 提供简体中文 Web 管理后台、单管理员登录和 CSV 历史导出。
- 提供最新榜单快照页；封面支持无图、强模糊和正常三种全局显示模式。
- 提供 `amd64`、`arm64` Docker 镜像构建能力和 Docker Compose 示例。

### 5.2 明确不做

- qBittorrent、Transmission、迅雷或 p115 直连。
- PT 站、保种、辅种、分享率、免费种或促销规则。
- `.torrent` URL、`.torrent` 上传和纯 BitTorrent v2 `btmh`。
- 通用可视化 RSS/HTTP 数据源编辑器。
- 运行时安装第三方插件或在线插件市场。
- 多 CloudDrive2 实例、复杂路由和路径模板。
- 自定义 Cron、错过任务补跑和分布式任务队列。
- Telegram、微信、邮件等通知。
- 多用户、角色、组织、租户或公网 SaaS。
- 演员、厂牌、剧情等详情级媒体刮削和媒体库管理。
- Emby、Plex、Jellyfin 入库。
- 删除外部 CD2 任务或 115 文件。
- 原始网页/API 响应长期保存。
- 完整移动端 App；首版仅保证基本响应式操作。
- 遥测、使用数据上报、自动更新和自动降级数据库。
- 自动操作浏览器、提取登录 Cookie、绕过验证码、付费墙或反机器人验证。

## 6. 核心概念

| 概念 | 定义 |
|---|---|
| Provider | 将一种外部来源转换为 Tuntu 领域对象的 Python 实现 |
| Discovery Source | 产生用户“想找什么”的榜单来源 |
| ContentItem | 内容中立的待查找条目，由命名空间和规范化标识唯一确定 |
| Candidate Source | 为 ContentItem 查找公开 BitTorrent magnet 的来源 |
| Candidate | 一个由 BTIH 唯一识别的 magnet 候选及其属性和来源证据 |
| Evidence | 来源对排名、标题、体积、做种数或内容属性给出的证据 |
| RuleSet | 对 Candidate 做接受或拒绝判断的一组规则 |
| Evaluation | 某个候选在某次运行中的规则结果与原因 |
| Profile | 一项订阅，包含来源、榜单周期、规则、Top N、目录、每日时间和自动提交开关 |
| Run | 一次发现、清洗、选择与提交过程，保存不可变配置快照 |
| DownloadTask | 一次对 CloudDrive2 的外部提交及后续状态历史 |

## 7. 目标用户与使用场景

### 7.1 自动榜单订阅

用户建立一个 JavDB 周榜订阅，选择多个候选源和过滤规则。Tuntu 每天在固定时间遍历榜单，默认仅预演；用户确认规则后开启自动提交，合格磁力下载到用户配置的“CD2 全局根目录 + Profile 子目录”。`/115open/Tuntu/jav-weekly` 只能作为文档示例，不能写死在程序中。

### 7.2 手工番号补充

用户选择一个现有 Profile，输入一个番号。Tuntu 继承该 Profile 的候选源、规则、排序和目标目录，展示候选及筛选原因，再由用户确认提交。

### 7.3 直接 magnet

用户选择 Profile，粘贴 magnet，可选填写标题。系统预览 BTIH、目标目录和去重结果；普通提交确认一次，绕过去重或重复下载时二次确认。

### 7.4 故障排查与补录

用户从仪表盘看到来源异常或下载进入“需要关注”，查看证据和错误。如果已经在 CD2/115 中确认文件存在，可以二次确认后手工标记完成；系统明确记录这是人工结论。

### 7.5 关注清单

用户可以创建人物、系列或关键词清单，批量导入作品标识与元数据，并记录待处理、已有、忽略及真实下载状态。批量导入不得包含 magnet、torrent 或下载地址；单项下载必须由用户提供有权使用的 magnet，并显式确认权利和提交动作。

## 8. 主要用户流程

### 8.1 首次初始化

1. 容器首次启动时在日志输出一次性 Setup Token。
2. 用户打开设置页，用 Setup Token 创建唯一管理员密码。
3. Setup Token 立即失效。
4. 用户配置 CloudDrive2 地址、凭据和全局保存根目录。
5. 用户执行连接测试，并使用合法公开测试 magnet 验证保存目录和完成检测。
6. 用户创建第一个 Profile；新 Profile 默认处于预演模式。

忘记密码时，用户在容器内执行 CLI 重置命令，生成新的 Setup Token。重置密码后所有旧会话失效。

### 8.2 自动运行

1. 每日计划到点后，系统尝试为 Profile 创建 Run。
2. 若同一 Profile 已有运行中 Run，本次触发被跳过并记录原因。
3. Discovery Sources 返回 ContentItem；系统按规范化标识合并重复内容和排名证据。
4. Candidate Sources 查询 magnet；系统验证 URI、提取 BTIH、合并相同 BTIH 的证据。
5. 系统评估规则，并为每个拒绝保存明确原因。
6. 每个内容从合格候选中选出排序第一项。
7. 系统执行内容级和 BTIH 级全局去重。
8. 预演模式只记录将要提交的任务；自动模式向 CD2 提交。
9. Run 在发现、清洗、选择和提交阶段结束后终止；下载状态由后台异步轮询更新。

### 8.3 手工番号

1. 用户选择 Profile 并输入番号。
2. Provider 规范化番号，候选源查询并执行同一套规则和排序。
3. 页面展示候选、证据、拒绝原因、去重结果和目标目录。
4. 用户确认后提交所选候选。

### 8.4 直接 magnet

1. 用户选择 Profile、粘贴 magnet，可选填写标题。
2. 系统只接受含 BitTorrent v1 `btih` 的 magnet。
3. 页面展示规范化 BTIH、重复记录、目标目录和提交影响。
4. 普通提交确认一次；强制重复提交二次确认。

## 9. 功能需求

### FR-01 管理员、初始化与会话

优先级：P0

- 只支持一个管理员，不提供注册、角色和多用户。
- 首次初始化使用日志中一次性 Setup Token；使用后立即失效。
- 提供容器 CLI 密码重置，生成新的 Setup Token。
- 密码使用 Argon2id 或等效强哈希保存。
- 登录会话采用 7 天滑动有效期。
- 修改或重置密码后立即注销全部旧会话。
- Cookie 使用 `HttpOnly`、`SameSite`；使用 HTTPS 时启用 `Secure`。

### FR-02 系统设置与秘密

优先级：P0

- SQLite 是运行配置的事实来源；环境变量仅用于首次引导或覆盖秘密。
- 支持一个 CloudDrive2 实例，但该实例的全部环境相关字段必须可配置：
  - gRPC endpoint（协议、主机和端口）。
  - 认证方式：API Token（推荐）或用户名/密码；启用 2FA 的实例应使用 API Token。
  - API Token、用户名和密码等秘密字段。
  - TLS 验证开关和可选自定义 CA 证书。
  - 全局保存根目录和连接测试子目录。
  - 下载状态轮询间隔与“需要关注”超时。
- 产品代码不得内置开发者 NAS 地址、端口、账号、Token、云盘名或 `/115open` 等路径。
- CD2 API Token 的名称、根目录和权限由用户在 CD2 中创建；Tuntu 只读取 Token，并在连接测试时验证必要权限，不替用户写死或静默扩大权限。
- 自动下载要求 Token 具备列目录、读取属性、创建文件夹、添加离线任务和查询离线任务等最小权限；缺少创建文件夹权限时连接测试必须明确报告，不能回退到不可靠的共享目录归属。
- 保存根目录按当前凭据可见的 API 路径配置；若受限 Token 已把宿主目录映射为 `/`，Tuntu 使用 `/`，不得再次拼接宿主绝对路径。
- 支持一个可选的全局 HTTP/SOCKS5 出站代理。
- 公开互联网 Provider 默认继承代理；CD2 和其他局域网地址默认绕过代理。
- 设置页和 API 永不回显完整密码、Token 或 Cookie，只显示掩码和是否已配置。
- 用户可以通过环境变量注入秘密，也可以在设置页保存秘密。
- 保存的秘密位于权限受限的 `/data` 中；文档必须说明拥有数据卷权限的人仍可读取，不宣称其为绝对安全的加密保险箱。

### FR-03 Profile 订阅

优先级：P0

一个 Profile 包含：

- 名称、启用状态和归档状态。
- 一个榜单周期：日榜、周榜或月榜。
- 一个或多个与该周期匹配的榜单来源。
- 一个或多个候选磁力来源。
- 一个 RuleSet。
- `Top N`：默认 20，可配置范围 1–100。
- 用户可配置的固定 CD2 子目录；最终目录为“用户配置的全局根目录 + Profile 子目录”。
- 一个每日执行时间和时区。
- 自动提交开关，默认关闭，即默认预演。

其他要求：

- 自动订阅不能在没有榜单源或没有候选源时保存为启用状态。
- 支持立即运行和强制预演。
- 同一个 Profile 同时只允许一个 Run。
- “删除”实际为归档：停止计划任务但永久保留历史，可恢复。
- 不支持自定义路径模板、Cron 表达式和每个内容下载多份候选。

### FR-04 v0.1 内置来源

优先级：P0

发现入口：

- 手工番号。
- JavDB 网页日榜、周榜、月榜，以及按番号搜索详情后提取的磁力候选。
- JavDatabase 周榜 Feed。

候选来源：

- JavDB 详情候选。
- Sukebei RSS。
- Knaben API。
- Bitsearch API。

来源约束：

- v0.1 正式支持可稳定公开访问的接口或页面；JavDB 可例外使用管理员明确填写的会员 Cookie 和 User-Agent，但不读取浏览器存储、不代替用户登录，也不绕过验证码或访问挑战。
- 每个来源具有超时、有限重试、退避、速率限制和短期缓存。
- 同一 Run 内不得重复请求相同查询，相邻 Run 可以复用仍有效的缓存。
- 每个来源记录最近成功时间、延迟、结果数、连续失败次数和最近错误。
- 连续失败不会自动禁用来源；用户可以自行停用。
- 内置来源 endpoint 可在设置页或环境变量中覆盖，以适配镜像和反向代理。
- JavDatabase RSS 只用于定位最新一期，Provider 必须读取完整榜单文章，不能把摘要条数当成完整榜单。
- Provider 必须实现清晰的 Python 接口并使用离线 Fixture 测试。
- v0.1 不支持运行时安装第三方 Provider；1.0 前 Provider 接口允许调整。

### FR-05 内容规范化与榜单合并

优先级：P0

- ContentItem 使用 `namespace + normalized_key` 作为稳定身份。
- Provider 同时返回原始标识和规范化标识。
- JAV Provider 负责大小写、分隔符和数字补零等站点语义。
- 无法可靠规范化时使用“来源命名空间 + 原始 ID”，不得做模糊猜测。
- 同一内容出现在多个榜单时合并为一个 ContentItem，保留全部来源与排名证据。
- 默认展示最靠前的排名，候选查询和自动下载只处理一次。
- v0.1 保存标识、标题、排名、来源、候选、下载状态，以及榜单展示所需的封面 URL 和原始条目 URL。
- 不持久保存完整原始网页或 API 响应，只保存规范化字段、必要证据和错误摘要。
- 封面 URL 随内容快照持久化；无图模式不得在 HTML 中输出远程封面地址，模糊模式不得提供悬停解锁。

### FR-06 magnet 解析、候选合并与属性证据

优先级：P0

- 只接受包含 BitTorrent v1 `btih` 的 magnet。
- 兼容 40 位十六进制和 32 位 Base32 BTIH，统一规范为小写十六进制。
- 相同 BTIH 不受显示名称、Tracker 或参数顺序差异影响，合并为一个 Candidate。
- 候选身份只看 BTIH，但向下载客户端提交时保留显示名、Tracker、webseed、精确来源和非 v1 `xt` 等传输提示；重复 v1 BTIH 只发送一个规范值。
- 合并时保留所有来源证据，不把冲突值静默覆盖成确定事实。
- 中文字幕、无码状态和 UHD 使用三态值：`yes`、`no`、`unknown`，并记录判定证据。
- 体积和做种数允许未知；未知不得伪装成 `0`。
- 无效 URI、缺失 BTIH 和纯 `btmh` 候选不能进入自动提交。

### FR-07 规则、排序与选择

优先级：P0

新 Profile 默认不偏好中文字幕、无码、UHD、体积或做种数，只执行有效性清洗。

规则字段：

- 中文字幕：不限、仅中文、排除中文。
- 无码状态：不限、仅无码、仅有码。
- UHD：不限、仅 UHD、排除 UHD。
- 最小体积和最大体积（MB）。
- 最少做种数。
- 标题必须包含关键词、标题不得包含关键词。

规则语义：

- 三态字段的“仅”规则只接受 `yes`；“排除”规则只拒绝 `yes`，`unknown` 保留。
- 当启用体积上下限但体积未知时，候选不能证明满足规则，应拒绝并注明“体积未知”。
- 当启用最少做种数但做种数未知时拒绝并注明“做种数未知”。
- 关键词忽略大小写，使用普通文本而非正则表达式。
- 多个“必须包含”关键词采用任一匹配；多个排除词命中任意一个即拒绝。
- 一个候选可以同时保存多个拒绝原因。

默认排序：

1. 已知做种数排在未知之前，做种数从高到低。
2. 已知体积排在未知之前，体积从小到大。
3. 使用规范化 BTIH 和来源名称形成稳定排序。

不同候选源不设置人工优先级。同一 BTIH 的来源元数据合并，来源名称只参与最后的稳定排序。自动流程每个 ContentItem 只选一个候选。

### FR-08 候选结果与可解释性

优先级：P0

- 榜单条目没有候选时记录 `no_candidate`，不视为系统错误。
- 候选全部被过滤时记录 `filtered`，不视为系统错误。
- 每个候选保存接受或拒绝结论、全部规则原因和证据。
- 预演结果必须展示：内容、排名来源、候选来源、BTIH、体积、做种数、三态属性、规则结论、去重结论和目标目录。
- 配置变更只影响下一次 Run；历史页面始终展示该 Run 的不可变配置快照和原始结论，不使用新配置重新评估。

### FR-09 全局去重、幂等与候选回退

优先级：P0

- 同一 CD2 实例内对内容身份和 BTIH 做全局去重，跨 Profile 生效。
- 相同内容已由其他 Profile 提交时，新 Profile 记录“已由 Profile X 处理”，不因目录不同重复提交。
- 一个内容一旦有任务被 CD2 接受，不再自动切换到其他 BTIH。
- 提交前的明确同步拒绝可以尝试该内容的下一个候选。
- 网络超时或结果不明确时，只重试同一个候选，不得切换到其他候选。
- CD2 接受后的下载失败必须人工处理，不自动换磁力。
- 普通 `failed` 任务可以重试；`submitted` 或 `completed` 的强制重提需要二次确认。
- 直接 magnet、重复内容或绕过去重的强制提交需要二次确认。
- 所有强制操作保留新旧任务关联和审计记录。

### FR-10 CloudDrive2 下载客户端

优先级：P0

- v0.1 只实现一个 DownloadClient：CloudDrive2。
- 使用 CloudDrive2 官方 gRPC，支持连接测试、magnet 提交、指定保存目录、任务状态查询和文件树查询。
- 目标目录只能由已验证的全局根目录和固定 Profile 子目录组成。
- Tuntu 在固定 Profile 目录下使用完整 BTIH 作为内部任务隔离子目录，以支持同一 Run 批量提交并可靠归属完成证据；这不是用户自定义路径模板。
- 系统不得以空路径、未解析环境变量或意外根目录提交。
- 不删除、取消或清理外部 CD2 任务及 115 文件。
- `DownloadClient` 领域接口保持内容无关，为后续 qBittorrent 等实现留边界。

### FR-11 DownloadTask 状态

优先级：P0

状态定义：

| 状态 | 含义 |
|---|---|
| `submitting` | 正在向 CD2 提交，结果尚未确定 |
| `submitted` | CD2 已明确接受任务 |
| `downloading` | 有可靠证据表明任务正在下载 |
| `completed` | 有可靠证据表明目标文件已完成 |
| `failed` | CD2 明确拒绝或任务明确失败 |
| `attention_required` | 长时间无法可靠确认进展，需要人工检查 |

状态要求：

- 每次状态变化保存时间、证据、错误分类和原因。
- 未结束任务的轮询间隔可配置，默认 5 分钟。
- “需要关注”超时可配置，默认 24 小时；到期后进入 `attention_required`，但继续保持内容和 BTIH 去重锁。
- `completed` 必须来自 CD2 任务 API，或相对提交前目录基线新增/变化的文件集合、文件数和总大小经过至少两次成功观察保持稳定。
- 任务状态查询超时不得覆盖可用的文件树证据；同目录并发导致证据无法唯一归因时进入 `attention_required`。
- 用户可二次确认后手工标记完成，事件必须显示“人工确认”，不能伪装成自动确认。
- 如果无法实现至少一种可靠完成信号，产品只能作为原型，不得发布正式 v0.1。

### FR-12 Run、调度与故障语义

优先级：P0

- 每个 Profile 支持一个每日执行时间和手工立即运行。
- 服务停机时错过的计划不补跑，等待下一计划时间；用户可手工运行。
- 不同 Profile 可以并行，但使用小型全局并发上限保护来源和 CD2。
- Run 在发现、清洗、选择和提交结束后终止；外部下载状态异步更新。
- Run 保存触发方式、开始结束时间、配置快照和各阶段统计。

Run 状态：

- `success`：所有请求正常结束；即使榜单为空、没有磁力或全部被过滤也算成功。
- `partial`：至少一个来源、条目处理或提交失败，但榜单阶段仍产生了可继续处理的结果；榜单成功而候选源全部失败时也属于 `partial`。
- `failed`：所有榜单来源都失败，或运行环境无法初始化。

来源返回空集合是正常成功，不等于来源故障。个别候选源失败不会丢弃其他来源结果。

### FR-13 Web 管理后台

优先级：P0

v0.1 提供以下简体中文页面：

- 首次设置与登录。
- 仪表盘：最近运行、下载状态、异常来源和需要关注项。
- 热榜：显示最近一次有效 Run 的完整排名快照、封面和来源链接，并可按订阅切换。
- 关注清单：创建人物/系列/关键词清单，导入元数据，查看处理与下载状态。
- 订阅列表与编辑页。
- 手工番号/直接 magnet 页面。
- 单次 Run 详情及候选筛选原因。
- 下载记录与状态事件。
- 数据源健康状态。
- 系统、代理、来源 endpoint、热榜封面模式与 CD2 设置。

交互要求：

- 桌面优先，手机上至少能查看状态、暂停订阅和执行紧急操作。
- 页面使用服务端渲染和少量原生 JavaScript/CSS，不建立独立前端构建链。
- 普通提交预览后确认一次；强制重复、人工完成等高风险操作二次确认。
- v0.1 不发送通知，异常只在仪表盘展示。

### FR-14 REST API

优先级：P0

- Web UI 通过同源、版本化 `/api/v1` REST API 工作。
- API 使用管理员网页登录会话认证。
- v0.1 不为 **Tuntu 自己的 REST API** 提供独立 API Token，也不承诺 1.0 前的第三方 API 稳定性；这不影响 Tuntu 使用用户配置的 **CD2 API Token** 连接下载器。
- 错误响应使用稳定错误码和可读摘要，不向页面暴露堆栈。
- 关键写操作记录审计事件。
- 提供 `/health` 和 `/ready`。

### FR-15 记录、保留与导出

优先级：P0

- 规范化 ContentItem、Candidate、Evidence、Evaluation、Run 和 DownloadTask 历史无限期保留，除非未来用户主动执行数据清理功能。
- 不保存完整原始网页/API 响应。
- 提供下载历史 CSV 导出，至少包含：内容标识、标题、榜单来源、排名、BTIH、候选来源、筛选结果、Profile、目标目录和各阶段时间。
- v0.1 不提供历史导入和 UI 备份恢复。

### FR-16 数据迁移、备份与升级

优先级：P0

- 所有持久数据统一位于 `/data`。
- 应用启动时自动执行事务化数据库迁移。
- 迁移前自动备份 SQLite，并只保留最近 3 份自动迁移备份。
- 迁移失败时拒绝启动，不得带着半迁移数据库继续运行。
- 不支持数据库直接降级。
- 文档提供整个 `/data` 和 SQLite 的手工备份、恢复与升级步骤。

### FR-17 日志、隐私与遥测

优先级：P0

- 结构化运行记录保存于数据库；普通文本日志默认轮转并最多保留 30 天。
- 日志包含必要的 `run_id`、`profile_id`、`source` 和 `task_id`。
- 日志、API 和错误摘要不得包含完整 Cookie、密码、Token、Authorization 或秘密 URL 参数。
- 不采集遥测，不上报使用数据，不自动检查或安装更新。

## 10. 数据模型要求

v0.1 至少需要以下持久化实体：

| 实体 | 用途 |
|---|---|
| `users` | 唯一管理员、密码哈希与会话失效版本 |
| `sessions` | 可撤销的管理员会话 |
| `setup_tokens` | 一次性初始化/重置令牌的哈希与失效时间 |
| `settings` | 系统、代理、CD2 和非秘密设置 |
| `profiles` | 订阅、规则、目录、Top N、每日时间与归档状态 |
| `watchlists` / `watchlist_items` | 关注对象、别名、关联作品、人工状态与元数据来源 |
| `profile_sources` | Profile 选择的榜单源和候选源 |
| `runs` | 运行状态、触发方式、统计和不可变配置快照 |
| `run_source_results` | 每个来源在 Run 中的耗时、数量和错误 |
| `content_items` | `namespace + normalized_key` 的规范化内容 |
| `run_items` | 内容在某次 Run 中的来源、排名和处理结果 |
| `candidates` | 规范化 BTIH 和候选当前聚合信息 |
| `candidate_evidence` | 来源对标题、URI、体积、做种数和三态属性的证据 |
| `evaluations` | 某次 Run 中候选的规则结果和原因 |
| `download_tasks` | CD2 提交、当前状态、幂等代次和人工标记 |
| `download_events` | 下载状态变化与证据历史 |
| `source_health` | 来源最近健康状态和连续失败信息 |
| `audit_events` | 强制提交、密码操作、人工完成等关键操作 |

关键约束：

- ContentItem 唯一键：`namespace + normalized_key`。
- Candidate 唯一键：规范化 BitTorrent v1 BTIH。
- 自动下载幂等范围：`CD2 实例 + ContentItem` 与 `CD2 实例 + BTIH`。
- Run 配置快照和 Evaluation 一经结束不得被后续 Profile 修改覆盖。

## 11. 非功能需求

### 11.1 架构与维护性

- Python 3.12、FastAPI、SQLAlchemy 2、Alembic、SQLite、Jinja2 和少量原生前端代码。
- API、调度器和轻量后台任务运行在同一进程。
- v0.1 只支持单实例、单进程，不引入 Redis、Celery 或独立 Node 构建链。
- 核心领域逻辑不依赖 FastAPI、ORM 或具体 Provider。
- Provider 和 DownloadClient 使用清晰的 Python `Protocol`/接口。
- Provider 接口在 v0.1 视为实验性，不提供运行时第三方安装和兼容承诺。

### 11.2 可靠性

- 外部请求必须有超时、有限重试、退避、缓存和并发上限。
- 数据库写入、状态迁移、下载占位和幂等检查必须使用事务。
- 不因单条坏数据中止整批运行。
- 服务重启后订阅、Run 和 DownloadTask 状态不丢失，也不重复提交。
- 轮询错误不得覆盖最后一个可靠状态。

### 11.3 性能

- Profile 单次最多处理 100 个 ContentItem，默认 20。
- Provider 并发采用小型可配置上限，默认不超过 4。
- 列表 API 分页；常用后台页面在家庭 NAS 上保持可交互。
- 性能优化不得牺牲来源速率限制和可追溯记录。

### 11.4 安全

- 目标部署是可信局域网；文档仍应建议用户通过反向代理启用 HTTPS，避免直接暴露公网。
- Docker 进程默认非 root，`/data` 使用独立持久卷和最小文件权限。
- 所有输入限制长度；目标路径必须规范化并限制在配置根目录下。
- 测试与公开仓库使用虚构数据和固定 Fixture，不提交真实成人磁力或秘密。
- CD2 集成与发布验收只使用合法公开测试资源。

### 11.5 部署与兼容

- 官方只支持 Docker 和 Docker Compose。
- 镜像目标平台为 Linux `amd64` 和 `arm64`。
- 端口和时区可配置，持久目录固定为 `/data`。
- 应用不自动更新；用户通过拉取新镜像升级。

## 12. 验收场景

### AC-01 首次设置与会话失效

全新 `/data` 启动后，日志只生成一个有效 Setup Token；创建管理员后 Token 失效。修改密码后旧会话不能继续访问。

### AC-02 多榜单合并与预演

Profile 使用同周期多个榜单源，Top N 为 20。相同番号合并为一个内容并保留全部排名证据；预演展示候选、规则结果、去重和目标目录，且不创建外部任务。

### AC-03 候选多源聚合

至少两个候选源返回包含同一 BTIH 的不同 magnet。系统规范化并合并为一个 Candidate，保留两个来源证据，不受 Tracker 和显示名称差异影响。

### AC-04 三态规则与解释

对 `yes`、`no`、`unknown` 的中文字幕/无码/UHD Fixture 执行规则，结果符合第 9 节语义；体积或做种数规则遇到未知值时明确拒绝。每个拒绝项均显示原因。

### AC-05 手工番号与直接 magnet

手工番号继承所选 Profile 的候选源、规则、排序和目录。直接 magnet 能预览 BTIH 和去重结果；纯 `btmh` 或无 BTIH 输入被拒绝。

### AC-06 全局去重

两个 Profile 发现同一内容或 BTIH 时只产生一次自动提交。后发现的 Profile 显示原 Profile 和任务关联；强制重提必须二次确认并记录审计事件。

### AC-07 候选回退

CD2 明确同步拒绝第一候选时可以尝试下一候选；网络超时或结果不明确时只能重试原候选；CD2 接受后的失败不自动换候选。

### AC-08 来源部分失败

一个来源超时而其他来源成功时，Run 为 `partial` 且成功数据完整保留。所有榜单来源失败时 Run 为 `failed`；正常空结果为 `success`。

### AC-09 CD2 合法测试下载与完成

合法公开测试 magnet 被提交到指定测试子目录。系统先记录 `submitted`，再根据可观察证据更新为 `downloading`（如客户端可提供）和 `completed`；容器重启后状态与幂等锁仍存在。

### AC-10 需要关注与人工完成

任务超过用户配置的“需要关注”阈值（默认 24 小时）仍无可靠进展后进入 `attention_required` 且不自动换磁力。用户二次确认后可人工标记完成，事件明确标注人工来源。

### AC-11 调度与配置快照

同一 Profile 的重叠触发被跳过，不同 Profile 可受控并行。服务停机期间错过的每日任务不补跑。修改规则不会改变历史 Run 的快照和结论。

### AC-12 秘密与日志

检查设置 API、页面、错误响应和轮转日志，不出现 CD2 密码、Cookie、Token 或完整 Authorization；日志保存不超过配置的 30 天。

### AC-13 迁移、备份与恢复

从旧 Schema 启动时先生成备份再成功迁移；故意制造迁移失败时应用拒绝就绪，原数据库可从自动备份恢复，备份最多保留 3 份。

### AC-14 CSV 与归档

下载历史可导出约定字段。归档 Profile 后不再调度，但历史、下载记录和审计事件仍存在，恢复后可继续运行。

### AC-15 Docker 构建

`amd64` 和 `arm64` 镜像均完成构建验证；Compose 使用 `/data` 卷启动，健康检查、初始化和优雅退出正常。

## 13. v0.1 发布条件

只有以下条件全部满足，才能标记 `0.1.0`：

- 至少一个真实榜单源稳定获取并规范化数据。
- 至少两个候选源完成聚合和 BTIH 去重。
- 手工番号和直接 magnet 流程可用。
- 规则过滤能解释每次接受与拒绝。
- 全局去重、候选回退、重试和强制操作符合本 PRD。
- 每日计划、手工运行和默认预演可用。
- CD2 将合法测试 magnet 下载到指定目录。
- 至少一种可靠完成信号经过实机验证；人工确认只能作为补充，不能替代自动完成能力。
- 重启后订阅、运行、下载状态和幂等锁不丢失。
- 登录、密钥遮蔽、日志脱敏、备份和数据库迁移通过测试。
- Docker `amd64`、`arm64` 完成构建验证。
- 核心管线、规范化、规则、排序、状态机和去重具备自动化测试。
- AC-01 至 AC-15 全部通过。
- 不存在已知的批量重复提交、秘密泄露或数据丢失高优先级问题。

如果 CloudDrive2 无法提供任务状态，且也无法通过目标目录可靠确认完成，则项目只能发布预览版，不得宣称 v0.1 核心闭环已经完成。
