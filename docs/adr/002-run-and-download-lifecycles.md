# ADR-002：Run 与 DownloadTask 生命周期

- 状态：已接受
- 日期：2026-08-13
- 适用版本：v0.1

## 背景

榜单扫描通常在几秒或几分钟内结束，但外部下载可能持续数小时。若把两者合成一个长任务，调度互斥、重启恢复、运行统计和下载状态都会变得含糊。

## 决策

1. `Run` 只负责发现、候选查询、清洗、规则评估、选择、去重和提交。
2. 提交阶段结束后 Run 立即终止，不等待 CD2 下载完成。
3. 每个 Run 保存不可变 Profile 配置快照和每个来源、内容、候选的处理结果。
4. Run 状态只有：
   - `success`：所有请求正常完成，空榜单、无候选和全部过滤也属于成功。
   - `partial`：存在来源、条目或提交失败，但榜单阶段仍有可处理结果。
   - `failed`：所有榜单来源失败，或运行环境无法初始化。
5. `DownloadTask` 独立保存外部提交与状态事件，由后台轮询更新。
6. 同一 Profile 同时只允许一个 Run；不同 Profile 在小型全局并发上限内运行。
7. 每个 Profile 只有一个每日时间；服务停机期间错过的计划不补跑。
8. 应用重启后恢复未结束 DownloadTask，但不重放已结束 Run。

## 结果

- Run 的耗时与统计不受外部下载速度影响。
- 历史规则结论可由配置快照准确解释，Profile 后续修改不会改写旧记录。
- 调度器、Run Service 和下载轮询器必须共享数据库幂等约束，但保持独立事务边界。
- UI 必须分别展示“本次运行结束”和“下载任务完成”，不能使用一个模糊进度表示两者。

## 不采用的方案

- Run 一直保持运行到文件完成：会长期占用互斥锁，重启语义复杂。
- 启动后补跑所有错过计划：可能在 NAS 恢复时批量提交。
- 用内存保存运行结果：重启后无法审计，也无法保证幂等。
